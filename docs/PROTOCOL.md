# 莫比 (Mobi) 椭圆机蓝牙协议分析

English version: [PROTOCOL.en.md](PROTOCOL.en.md)（两份文档需保持一致）

|---|---|---|
| `mobi莫比健身_3.5.9.1_APKPure.apk` | `com.anytum.mobi` | 3.5.9.1 (versionCode 134) |

## 1. 协议识别（BaseHandler.createHandler）

连接后先申请 MTU 128，然后按服务判断：

1. 有 `0x8800` → **2.0 协议**
2. 有 `FFE0` → **1.0 协议**
3. 有 `FFF0`，且设备名以 `MOBI-` 开头、不以 `MOBI-C` 开头 → **环通协议**（`MOBI-E…` 为椭圆机）
4. 有 `0x1826` → **FTMS**
5. （3.5.9.1）其余带 `FFF0`/`FFC0` 的设备按 1.0 处理

同一台机器可能同时带多个服务（例如既有 FTMS 又有私有服务）。官方按上面的顺序**优先使用私有协议**。通用椭圆机 App 一般直接走 FTMS，阻力异常的原因很可能就在这里。

## 2. 2.0 协议（服务 0x8800）

| 特征 | 方向 | 内容 |
|---|---|---|
| 8801 | 读 | `[0]` 数据上报模式。1 = 用 8811 算踏频；2/3 = 用 8813 汇总数据；bit1 置位表示需要开始/停止指令 |
| 8802 | 读 | `[0]` 设备类型（11=椭圆机，10=单车，9=划船机，12=跑步机），`[1]` 子类型 |
| 8805 | 读 | `[0]` 磁铁数（算踏频用） |
| 8806 | 读 | `[0]` 读写模式码，`[1]` 最小阻力，`[2]` 最大阻力 |
| 880E | 通知 | 机器状态 0 停 / 1 运行 / 2 暂停 |
| **88FF** | 写 | **解锁写权限：`11 82 07`** |
| **880F** | 写 | **控制指令** |
| 8811 | 通知 | u16 大端，转一圈的毫秒数；rpm = 60000 / 间隔 / 磁铁数 |
| 8812 | 读/通知 | `[0]` 当前阻力档位 |
| 8813 | 通知 | `[0]` 速度/10，`[2]` 踏频，`[3..4]` 时长，`[5..6]` 距离，`[7..8]` 热量/10（大端） |

**阻力指令**（`V2Handler.bleVer0x02Control`，commandCode 4）：

```
每次连接后先写一次：  88FF ← 11 82 07
然后：                880F ← 02 LL VV
```

`VV` 是档位。`LL` 是档位的**十进制位数**，代码是 `String.valueOf(level).length()`，不是字节数：

| 档位 | 指令 |
|---|---|
| 5 | `02 01 05` |
| 12 | `02 02 0C` |
| 24 | `02 02 18` |

自己写 App 时常见的两个错误：

- 不写 88FF 解锁。盒子收下 880F 的写入，但不执行。
- 第二字节写成固定 `01`。档位 10 以上的指令格式不对。

其他 880F 指令：`03` 停止、`04` 开始、`05` 暂停（只在 8801 bit1 置位时发送）、`00 LL VV` 速度、`01 01 VV` 坡度。

**型号表**（8806 读不到时使用，4.5.17）：

| 椭圆机子类型 | 模式 | 最大档位 |
|---|---|---|
| 1 | 0（官方 UI 不显示阻力） | 24 |
| 17 | 3 可读写 | 24 |
| 18 (MEH3205) | 2 只读 | 8 |
| 19 (MEH3204)、20 (MEH3201)、21 | 3 可读写 | 24 |
| 22 | 3 可读写 | **40** |
| 其他 | 0 | 24 |

8806 `[0]` 的映射（`getReadWriteMode`）：0→0，4→1 只写，5→3 可读写，其余→2 只读。

## 3. 1.0 协议（FFE0，0xAB 帧）

订阅 FFE0/FFF0/FFC0 下的 FFE4、FFE1、FFEA、FFF4、FFEB（名字以 `MB-HW` 开头的盒子，FFE4 要延迟 2 秒再订阅）。

状态帧：

```
AB 04 st TT SS bb xx i0 i1 i2 i3 .. .. RR
TT=类型(11 椭圆机) SS=子类型 bb=电量 i0..i3=转一圈毫秒数(大端) RR(第13字节)=当前阻力
```

**阻力指令**（`writeBleVer0x01Resistance`），写 FFE0/FFE3：

```
AB 03 00 TT SS LV xx
```

`TT`、`SS`、`xx` 必须**从机器最近一次上报的帧里原样拷贝**（第 3、4、6 字节），`LV` 为档位。所以：

- 机器还没发帧时（没通电、没踩动）发不了指令；
- 用固定值或 0 填充的帧，盒子会忽略。

踏频：rpm = 60000 / 间隔；子类型 17 再除以 2。

## 4. 环通协议（FFF0，名字 `MOBI-E…`）

这块主板**没有一次性设置阻力的指令**。官方流程（`HuanTongHandler`）：

1. 订阅 FFF1 成功后，写体重到 FFF2：`40 00 LB KG CS`，LB = kg × 2.2046226，CS = (0x40+LB+KG) & 0xFF
2. 之后**整个运动过程中每 1 秒**写一次：

```
FFF2 ← 20 C1 LV 00 CS        CS = (0x20 + 0xC1 + LV) & 0xFF
```

（`0xC1` 在反编译代码里显示为 `Collation.LONG_PRIMARY_CE32_LOW_BYTE` = 193，是编译器复用的常量。）

只写一次时，阻力会短暂变化后回落，或者完全不生效。这和“连上了但阻力调节不正常”的现象一致。主板不回报阻力，官方把它标为只写（模式 1），范围 1–24。

踏频：12 字节的 FFF1 帧，`[1] != 0` 时，`[2]`、`[3]` 按 `"%X%02X"` 拼成字符串，再按**十进制**解析（BCD）：`01 23` → 123 rpm。

## 5. FTMS（0x1826，莫比变体）

| 项目 | 官方做法 | 通用 FTMS 客户端常见做法 |
|---|---|---|
| 开始 | 先写 `00`（请求控制权），然后才订阅其他特征 | 先订阅 2AD9 指示 |
| 设置阻力 `04` | **`04 PP`，PP 只有 1 字节 = 档位 × 10** | `04 lo hi`（SINT16）或直接写档位 |
| 2AD6 范围 | min/max 为 SINT16 × 0.1 | 同左 |
| 2ACE 椭圆机数据 | 标志位通常 **2 字节**（`MB-E1010`、`Fibonacci` 是 3 字节），按包长自动判断 | 按规范固定 3 字节，后面的字段整体错位 |
| 2ACE 阻力字段 | SINT16 × 0.1 | — |
| 开始 / 停止 / 暂停 | `07` / `08 01` / `08 02` | — |

写成 `04 08`（意思是 0.8 档）而不是 `04 50`（8 档），机器会停在最低档。改用 2 字节编码后，后面多出来的字节也可能被丢掉或被误读。

## 6. 通用注意事项

- 官方用 `BleGattMangerQueue` 把所有 GATT 操作串行化：等上一个回调回来才发下一个。Android 上连续调用 `writeCharacteristic` 时，第二次会返回 `false`，指令直接丢失（比如解锁后马上写阻力）。
- 写类型沿用 Android 按特征属性选的默认值（支持无响应写时用无响应写），和 FastBle 一致。
- 官方界面把档位限制在 1–24，按原值下发，不做比例换算。

## 7. 锻炼数据（时长、里程、热量、心率）

官方的运动状态机（4.5.17 `com/anytum/mobi/motionData/MotionData.java`，3.5.9.1 `SportStateMachine.java`）：

- **数据来源**：机器自己上报总里程/总热量时（2.0 盒子 8813、FTMS 2ACE/2AD2）直接用机器的值；只上报踏频的机器（1.0 盒子、环通、8801 模式为 1 的 2.0 盒子）由 App 计算。
- **速度**：`speed(km/h) = rpm / 2.68`，椭圆机再 `/ 4`。60 rpm 约 5.6 km/h。
- **每秒累加一次**（`cumulativeData`，由 1 秒定时器调用）：`distance += speed / 3.6`，`calories += 每秒热量`。
- **停止踩动**：5 秒没有新踏频就把 rpm 清零（`zeroMovementData`），60 秒后自动暂停，600 秒后自动结束（默认值）。

热量公式（`SportStateMachineToolKt`，设置里可切换，默认老算法）：

| 算法 | 每秒热量 |
|---|---|
| 老算法 | `power/1000 + 体重/3600`。power 是 `exp(rpm/100)` 与 `exp(阻力×32/最大阻力/10)` 的二次曲面拟合；功率为 0 时热量为 0；椭圆机子类型 17 的功率 ×1.5 |
| 新算法 | `(表[min(96, 96/最大阻力×阻力)]/1000 × rpm × 60 + 0.058264444 rpm² − 4.3285 rpm + 125.303 + 12(阻力−1)/7 × (rpm/20 − 1.8)) / 3600`（括号内是每小时热量） |

用 60 rpm、最大阻力 24 计算（每分钟热量）：

| 阻力 | 新算法 | 老算法 |
|---|---|---|
| 5 | 5.2 | 5.1 |
| 10 | 7.9 | 8.4 |
| 16 | 11.5 | 16.2 |
| 20 | 14.2 | 约 25 |

“10 分钟 300 多卡”需要约 30 kcal/min，常见原因：

1. 新算法的结果是**每小时**热量，忘了 `/3600`；
2. 每收到一条蓝牙通知就累加一次（每秒可能有好几条），没有按经过的秒数累加；
3. 把机器上报的**累计总数**当作增量反复相加；
4. 停止踩动后还在用最后一次的 rpm 继续累加；
5. 老算法在高阻力时本身就偏高。

本 App 的处理（`workout/WorkoutTracker.kt`、`workout/CalorieModel.kt`）：

- 只在一个 1 Hz 循环里，按实际经过的时间累加，单次最多补 2 秒。
- 踏频超过 5 秒没更新就当作 0。
- 机器上报的累计值只取每秒的增量；计数器复位、单帧乱码都能处理；机器上报的字段一直是 0 时，改用公式计算。
- 每分钟热量上限 20 kcal。
- 默认使用新算法，另有热量系数可以校准。
- 只有“运动中”才计时；手动暂停、自动暂停（默认 60 秒）、断线都不计时。
